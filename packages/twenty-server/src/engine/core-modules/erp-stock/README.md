# ERP block «Склад» (erp-stock)

Серверная часть складского блока: правила проведения пяти товарных
документов (`goodsReceipt`, `goodsPosting`, `salesShipment`,
`stockTransfer`, `goodsWriteOff`), скользящая средняя себестоимость и
остатки (`ItemBalanceService`), guard-хуки на документы, строки и регистры
`stockLedgerEntry`/`itemBalance`. Метаданные объектов ставит SDK-приложение
(`packages/twenty-apps/internal/erp-stock`); этот модуль — только
код-сторона.

## Точность и округления

- Вся денежная математика — в целых копейках (утилиты
  `erp-sales/utils/erp-sales-money.util.ts`).
- **Средняя себестоимость (`avgCost`) хранится и считается в целых микро
  за единицу** (1 коп = 10 000 микро) — нативная точность CURRENCY-поля.
  Решение: округление средней до копейки на каждом пересчёте накапливало бы
  дрейф при цепочке приходов; микро-точность даёт ошибку ≤ 0,5 микро на
  пересчёт. Средняя округляется half-away-from-zero до целого микро.
- **Списание по средней**: `cost = qty × avgCostMicros / 10 000`,
  округление half-away-from-zero до копейки. Средняя при расходе не
  меняется.
- Приход: `newAvg = (oldQty × oldAvg + valueKopecks × 10 000) / newQty`.
  `applyReceipt` принимает **суммарную** стоимость прихода (не цену за
  единицу), чтобы перемещение оприходовало ровно ту сумму, что списана со
  склада-отправителя.
- Количества — float (NUMBER-поля); сравнения через `QTY_EPSILON = 1e-9`,
  остаток «около нуля» нормализуется в 0.

## Семантика qtyAfter

`qtyAfter` в строке `stockLedgerEntry` — остаток по паре item×warehouse
**после** этого движения (движения одного документа применяются к балансу
построчно, поэтому две строки одного товара дают нарастающий `qtyAfter`).
На сторно-строках ядро копирует `qtyAfter` исходной строки; после отката
балансов `cancelBalanceEffects` перештамповывает `qtyAfter` всех
сторно-строк пары значением остатка после отмены.

## Отмена (onCancel) — КРИТИЧЕСКИЙ контракт

Ядро (`PostingService.cancelInTransaction`) при отмене только вставляет
сторно-строки регистров и помечает исходные `isCancelled` — **`itemBalance`
ядро не трогает**. Поэтому onCancel КАЖДОГО из пяти документов вызывает
единую утилиту `ItemBalanceService.cancelBalanceEffects`, которая в той же
транзакции:

1. читает исходные (не сторно) строки `stockLedgerEntry` документа;
2. группирует дельты по item×warehouse (несколько строк одного товара
   откатываются одной дельтой, без промежуточного минуса);
3. под блокировкой проверяет, что остаток после реверса не уходит в минус —
   иначе `ErpPostingException` «Недостаточно остатка …» и откат всей
   транзакции отмены;
4. применяет обратную дельту к `actualQty`/`avgCost` и перештамповывает
   `qtyAfter` сторно-строк.

Упрощения (задокументированы сознательно):

- Отмена реализации/списания возвращает остаток по `costAmount`
  (`stockValueDiff`) строк — средняя сдвигается к цене возврата, но НЕ
  пересчитывается назад по истории движений.
- Если откат обнуляет количество, остаточная стоимость (дрейф средней)
  отбрасывается вместе с ним; средняя при нулевом остатке — информационная.
- `costAmount` строк и `totalCost` реализации при отмене не очищаются —
  остаются историей проведения.

Сопутствующее расширение ядра (задокументированное отклонение): в
`erp/utils/build-reversal-rows.util.ts` список негируемых мер дополнен
`stockValueDiff` — иначе сторно-строки `stockLedgerEntry` копировали бы
изменение стоимости без смены знака (список предшествовал контракту
регистра из Task 1).

## Остатки (`itemBalance`) и дедупликация

На `itemBalance` НЕТ unique-констрейнта по item×warehouse — дедупликация
на стороне сервиса: `pg_advisory_xact_lock(hashtextextended(...))` по паре
закрывает гонку get-or-create (`SELECT … FOR UPDATE` пустого результата
ничего не блокирует), затем `SELECT … FOR UPDATE` строки. Если дубликаты
когда-либо появятся, канонической считается старейшая по `createdAt`.
Строки баланса создаёт сам сервис (штампуя SYSTEM-актора); `name` =
«{товар} — {склад}».

## Документы

| Документ | Префикс | Движения | Особенности |
|---|---|---|---|
| goodsReceipt | GR | +qty по цене строки | `amount = qty×price` строк, `total` документа |
| goodsPosting | GP | +qty по цене строки | как receipt, без `total` (нет поля) |
| salesShipment | SH | −qty по средней | `costAmount` строк, `totalCost`; связанный `salesInvoice` (если задан) должен быть POSTED |
| stockTransfer | TR | −qty из From, +qty в To той же суммой | `warehouseFrom ≠ warehouseTo` |
| goodsWriteOff | WO | −qty по средней | себестоимость только в регистре (у строк нет поля) |

Валидации всех: ≥ 1 строки, `quantity > 0`, товар в каждой строке, склад в
документе; для приходных — `price ≥ 0`. Ошибка нехватки:
«Недостаточно остатка „{товар}“ на складе „{склад}“: доступно X, требуется Y»
(имена загружаются по id).

## Guards

Фабрики хуков переиспользованы из
`erp-sales/query-hooks/erp-sales-guard.pre-query.hooks.ts` (экспортированы
для блочных модулей): document-guard на 5 документов, line-guard на 5
строчных объектов, register-guard (безусловный блок, включая
upsert/restore/merge) на `stockLedgerEntry` и `itemBalance` — 11 операций
каждому объекту.
